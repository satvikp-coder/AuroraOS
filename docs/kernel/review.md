# Trusted review state machine (Cycle 20, Plan C1)

`kernel/ui/review.c` + `kernel/include/review.h`: the pure rules for "a person must look at exactly this change and approve it". It draws nothing, reads no input and changes no setting. **S1 execution stays disabled** (`env.review_path` is still 0): the compositor modal, the secure-attention routing and the S1 executor (Plan C2..C4) do not exist yet.

* One review at a time (`RV_E_BUSY`). Tickets strictly increase and are never reused; declined, expired, abandoned and consumed tickets are retired for good, so an old approval cannot be replayed.
* Only a validated S1 settings change can be opened (`aura_validate` + kind `AK_SET_SETTING`, status needs-approval, risk 1) and it is re-validated at execution.
* The approval is bound to the digest (FNV-1a 64 over an explicit little-endian serialisation) of every intent field (including all 48 preview bytes), the requester's pid, process generation, principal and nonce, and the previous and proposed values. `rv_verify` recomputes it from values re-read NOW and refuses on any difference.
* Timing (monotonic ms from the caller): the secure-attention gesture arms only >= 600 ms after opening (a held key or an immediate software gesture is a no-op); Approve works only < 10 s after arming (then it falls back to OPEN and says LAPSED); the review expires at 60 s; an approval nobody executes expires after 10 s. A clock that goes backwards counts as no time passed.
* `rv_approve` moves to APPROVED; `rv_verify` consumes it (DONE) exactly once; any failed verify retires the ticket. The requester exiting (or its generation being replaced) kills the review.
* **Limits:** the module cannot tell a person from software sending the same gesture. Trust rests on the compositor routing the gesture here only from the kernel's own keyboard path and never to a client (Plan C2); under QEMU the host/QMP can inject that gesture, so nothing here protects against a malicious host controlling the emulator.
* Tests: `tests/kernel-host/review_test.c` (49 checks incl. a 30,000-step randomized run against independently tracked invariants; 17 targeted mutants killed).

## The compositor modal (Cycle 21, Plan C2): wired, S1 execution still disabled
* `shell_review_open` (kernel code only) shows the modal for a validated S1 request: scrim + dialog on the compositor's SCRIM/MODAL layers, the fixed strip "AuroraOS secure review" (the only user of the new secure palette colour; black with white text in high contrast), "Requested by: <kernel name>", the canonical preview, "<Setting>: <previous> -> <new>", the risk line and a live status line. Cancel is added before Approve, so **default focus is Cancel**; Approve is "Approve (locked)" and not focusable until the review is armed, and arming never moves focus. Enter or Space on the default focus therefore DECLINES. Escape declines in every state; a click on the scrim does nothing.
* **Secure attention** is Ctrl+Alt+Delete, decided first in `route_client` from the kernel keyboard driver's modifier state. The chord's Delete key event (down, repeat and up) is always consumed and never delivered to a client, whether or not a review is open; it only arms an open review (>= 600 ms after it opened, not a held key). The modifier key presses themselves still reach a focused client. With no keyboard a review cannot open.
* Containment: while the modal is open `route_client` withholds every pointer and key event from clients, the Index and Aura input handlers and the other modals refuse to run, and focus cannot leave the modal. EL0 clients cannot create, move, answer, close or cover it: clients are drawn in the content band below the scrim, and no system call can open, arm or answer a review.
* Ending: Cancel/Escape retire the ticket; the 60 s expiry and the requester exiting (`reap()` -> `shell_review_requester_gone`) leave the modal up with a message and a Close button; Approve closes it and leaves a pending approval that only `shell_review_verify` (re-checking everything, consuming it once) can turn into permission to run. The kernel loop logs `shell: review open|state=|approved|closed`.
* **Limits:** under QEMU the host/QMP can inject the chord, so none of this protects against a malicious host controlling the emulator; the kernel and compositor are the trusted base.
* Tests: `tests/kernel-host/shell_review_test.c` (47 checks incl. geometry at 75..200% in both palettes and a 20,000-step randomized run; 11 mutants killed, 1 equivalent) and `tests/qemu/review-tests.sh` (32 checks on the real kernel with a demo and a hostile EL0 UI client running).

## Real S1 settings execution (Cycle 21): text size and theme from a typed Aura command
The chain, every step able to stop it and say so (code: `aura_s1_begin` / `aura_s1_complete` / `aura_s1_recover` in `kernel/ui/aura_exec.c`; kernel wiring in `shell_run.c`):

`parse -> validate -> broker REVIEW -> resolve previous/next through the registry -> trusted review -> [approved] health check -> broker decision AGAIN with a fresh nonce -> re-read the previous value -> rv_verify (every byte, both values, the requester) -> durable PRE record -> registry set -> read-back -> apply to the live shell -> durable POST record -> truthful message`.

* Only the trusted shell (requester pid 0) can start it; an EL0 requester, even one holding the settings right, never opens a review. The policy answers REVIEW only with a review path (a keyboard), a healthy Trail and the shell's explicit rights; with no keyboard, a read-only or missing disk, or a damaged ledger the command is refused with the reason and nothing changes. `broker_set_review_path` is 1 only when a keyboard is present.
* **No record, no change:** the PRE record (Trail kind 3, state 4, `arg` = the previous value) must be durably written before the registry is touched. The POST record carries state 1 (done) and the verified new value, or state 6 with the value the registry really returned. The pair is the receipt (the POST sequence number is shown: "Receipt #N.").
* **Not atomic, and it says so:** AuroraFS has no transactions, so the registry and the Trail are separate commits. Registry refuses or reads back something else -> "Not saved" / "Not confirmed" with a FAILED record carrying the real value and the interface unchanged. Setting saved but POST lost -> "Saved, but its record could not be written. No Undo." A crash after PRE leaves a PRE without a POST: `aura_s1_recover` (run inside `ledger_boot` BEFORE the boot marker) appends a FAILED "interrupted" record (reason 1) with the setting's real value; the Trail screen shows it as "Setting change interrupted".
* An approval is single use and is invalidated by: a changed byte of the request, a changed previous value (someone else changed the setting meanwhile), a revoked right, an unhealthy ledger, expiry, or the requester leaving. Relative requests ("bigger") step on the ladder 75/100/125/150/175/200 from the value read now; at the ends the command is refused as "already the largest/smallest" with no review.
* Theme (registry value 0/1/2) is stored and recorded but nothing draws a different theme yet; the review says "Stored only: no dark theme". High contrast is a session preference, not a registry setting, and is not part of S1. The shell holds no `CAP_SET_SYSTEM`.
* Tests: `tests/kernel-host/aura_s1_test.c` (50 checks, 14 mutants killed, a 4,000-chain randomized run) and `tests/qemu/s1-tests.sh` (the shipped kernel: cancel, Escape, a real approval that changes the interface and survives a restart with both records on the disk; read-only and no-disk refusals).
