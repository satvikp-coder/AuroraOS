# Durable Passport and Trail ledgers (Cycle 20, milestones B and C)

Source: `kernel/include/ledger.h` (protocol and crash analysis), `kernel/ui/ledger_store.c` (pure, host tested), `kernel/ui/ledger_kernel.c` (AuroraFS binding).

* Files `passport.v1` (560 B) and `anchor.v1` (32 B), owner `PRINCIPAL_PASSPORT` (0x7F000004), owner-only permission. No system call can name that principal, so no process can read, write, list or see them. Durable grants name a stable application principal and generation 0; instance-bound grants stay in RAM and never reach the disk.
* One mutation = write `passport.v1` (commit N+1) -> read back and compare -> write `anchor.v1` -> read back and compare -> replace the live table. OK is returned only then.
* Crash points (proved by the host test, which cuts the power before and after every one of the writes of a mutation script): before the passport write = not committed; between the files = committed, repaired at the next boot; after the anchor = committed. After any crash the table is exactly the state before or after the interrupted mutation.
* Unknown outcomes (FS_EUNCERTAIN, I/O errors, a failed read-back) freeze the ledger (`failed`): no mutation, no durable grant honoured, until the next boot reloads the disk, which is then authoritative. Definite refusals (no space, quota) change nothing and leave it healthy.
* At load: commit == anchor -> ok; passport exactly one ahead -> repair the anchor (deferred on a read-only disk); anything else -> `rollback-detected`; damaged -> `corrupt`; a newer container version -> `newer-version`. In all three the table is EMPTY (everything denied), mutations are refused and the files are never touched. Empty shells left by a creation that died inside its first write are treated as no ledger.
* `ledger_passport_ok()` is 1 only for `ok` (verified and writable). No disk / read-only / any failure => protected (S1+) actions must not run. RAM-only instance rights and the S0 paths are unaffected.

**Limits (stated plainly):** FNV and CRC-32 detect accidents, not a deliberate rewrite. The anchor is on the same writable disk, so an attacker who can write the disk can replace both files with an older consistent pair undetected (QEMU virt has no hardware counter or secure storage). What is detected: one file restored, deleted, truncated, damaged or edited, and every crash window above.

## Trail (`trail.v1`, owner `PRINCIPAL_TRAIL` 0x7F000005, 2000 bytes)
* Same protocol as the Passport: build the next chain in memory, write the whole fixed-size file, read it back, write the anchor (which now also vouches for **the number of records ever appended** and **the chain head**), read the anchor back, and only then replace the live chain. OK means the record is on the disk. The ring keeps the newest 48 records; evicted records are counted and their chain value stays the base, so what remains verifies.
* Records carry the kernel-attested requester, canonical action, decision, reason, actual outcome and a **monotonic uptime in ms** (never a wall-clock time). Kinds 12/13/14 are the ledger's own (grant, revoke, boot); a boot marker (kind 14) is appended at every boot. Auditing every Passport grant/revoke and every broker decision is wired in milestone D.
* At load, per file: count == anchor and head == anchor head -> healthy; exactly one record ahead and the anchor's head equals the chain minus its newest record -> a crash between the file and the anchor: verified and repaired; no anchor is accepted only for a first record. Anything else (behind, two or more ahead, same count but a different head, file deleted while the anchor vouches for records) is `rollback-detected`. A damaged chain keeps its verified prefix for display but is never extended.
* **Evidence hold:** if EITHER ledger is corrupt, newer-version or rolled back, the other becomes `held`: its verified data stays readable (Passport grants are still honoured for the paths that need no recording), but NO write of any kind happens, so the disk stays byte-for-byte as found. A damaged anchor makes both ledgers corrupt.
* `ledger_ok()` (both ledgers OK) is what an action that needs Passport AND Trail checks. Instance-bound grants and the S0 paths are unaffected.

**Failure recovery states for an append** (proved by cutting the power before and after every write, and FS_EUNCERTAIN at every write): *definitely not committed* (died before the Trail file was written); *committed, caller not told* (died between the Trail file and the anchor: the next boot repairs it); *committed* (anchor written). An append whose outcome is unknown returns `LG_E_UNKNOWN`, freezes the Trail for the rest of the boot and the next boot decides. The Trail never claims a record that is not on the disk.

**Not in this change:** the broker does not consult the ledger yet and does not write audit records (milestone D); the native Trail screen is milestone E.

## Broker enforcement (milestone D)
* `kernel/ui/broker_kernel.c` has NO grant table of its own any more. An EL0 requester's rights are read from the Passport at every lookup (`ledger_peek` by stable principal AND process generation): `PP_NAVIGATE` -> navigate, `PP_SETTINGS_PROPOSE` -> settings, `PP_TIMER` -> timer. The policy looks the requester up when it decides and `aura_run_queued` looks it up again at execution, so a revocation applies to a request that was allowed earlier but has not run yet.
* `broker_grant_navigate` is now a RAM-only, generation-bound Passport grant; `reap()` drops every grant of a dead generation. After a store failure the ledger honours only these instance grants (never a durable one that may have been revoked on the disk).
* The trusted shell (requester pid 0) keeps `BP_RIGHTS_ALL` as its own explicit authority, independent of the Passport, so navigation, the Clock and Aura timers keep working with no disk, a read-only disk or a damaged ledger. A client with every right still cannot use the shell's timer.
* `broker_env()` refreshes `passport`/`trail` from `ledger_passport_ok()` / `ledger_trail_ok()` on every decision. S3 therefore reaches the next missing dependency (`no_review`) only on a healthy ledger, and S1 now also needs the Trail (`no_trail`) after the review path: an action that must be recorded cannot run when the Trail cannot record it. Nothing S1+ runs yet: the review path and hold input still do not exist.
* Audit: `ledger_grant_audited` / `ledger_revoke_audited` append Trail kind 12/13 after the Passport commit (best effort: the grant stands and the audit rc is logged). Security refusals of an EL0 request (no right, stale or unknown requester) are appended to the Trail, at most 16 per boot; further ones are counted and logged as dropped, so a request flood cannot thrash the disk. Replays and "not a command" refusals are not recorded.
